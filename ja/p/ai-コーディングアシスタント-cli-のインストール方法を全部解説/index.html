まず理解する：インストールとは結局何をしているのか

どの方法であっても、コマンドラインツールのインストールがやっていることは、本質的に次の 3 つだけです。

  1. 実行ファイルを PC のどこかのディレクトリに置く（claude.exe、opencode など）。
  2. そのディレクトリの場所をシステムに教える（つまり PATH の設定）。これでどこでも claude と打てば見つけられるようになります。
  3. ついでに設定ファイルを書き込むこともある（~/.claude/、~/.config/opencode/ など）。

インストール方法ごとの違いは、**「この 3 つを誰がやってくれるか」**だけです。

  • 公式スクリプト：公式が用意したプログラムがやってくれる。
  • パッケージマネージャー：「パッケージマネージャー」というソフトがやってくれる。
  • 手動ダウンロード：自分でやる。
  • Docker：ホスト側ではなく隔離された箱の中に入れる。

ここを押さえれば、以下の方法はすべて理解できます。

8 つのインストール方法を順番に解説

公式ワンラインスクリプト

どんな形か：

1
2
3
4
5
6
7
8

# macOS / Linux / WSL
curl -fsSL https://xxx.com/install.sh | bash

# Windows PowerShell
irm https://xxx.com/install.ps1 | iex

# Windows CMD
curl -fsSL https://xxx.com/install.cmd -o install.cmd && install.cmd && del install.cmd

一語ずつ分解：

  • curl：ダウンロードツール。-fsSL は「静かに、失敗したらエラー、リダイレクトを追う、エラーを表示」。
  • | bash：ダウンロードした内容をそのまま bash に渡して実行させる。
  • irm：PowerShell のダウンロードコマンド（Invoke-RestMethod の略）。
  • | iex：ダウンロードした内容をそのまま iex に渡して実行させる（Invoke-Expression の略）。

つまり irm ... | iex と curl ... | bash は同じ考え方を 2 つのプラットフォーム向けに書いたものです：スクリプトをダウンロード → すぐ実行。

何をしてくれるか： システムを自動判定し（Windows か Mac、64 ビットか ARM）、対応するビルドをダウンロードし、ファイルを検証し、ディレクトリに配置し、PATH を設定します。打つのは 1 行だけ。

長所： 一番手間がない。多くの場合自動更新付き。Node.js などのランタイムを事前に入れる必要がない。

短所： 「ダウンロードして即実行」なので、実行前にスクリプトの中身が見えない。ドメインが公式であることを必ず確認する必要がある。

向いている人： 最速で入れたい人、公式スクリプトを信頼して構わない人。現在、ほとんどの AI CLI ツールで第一に推奨される方法です。

OS のパッケージマネージャー

どんな形か：

ツール プラットフォーム 例
Homebrew macOS / Linux brew install xxx
WinGet Windows winget install xxx
Chocolatey Windows choco install xxx
Scoop Windows scoop install xxx
apt Debian / Ubuntu sudo apt install xxx
dnf Fedora sudo dnf install xxx
pacman Arch Linux sudo pacman -S xxx
apk Alpine sudo apk add xxx

何か： OS やコミュニティが管理する「ソフトウェア倉庫」です。何を入れたいか伝えれば、倉庫からダウンロード・展開・設定・登録まで自分でやってくれ、以後のアップグレードやアンインストールも担当します。

長所： アップグレードとアンインストールが整然としている。システムとの統合が良い。インストール先を覚えなくてよい。

短所： 倉庫のバージョンは遅れがち。新しく出た AI CLI ツールの多くはそもそも倉庫に入っていない。

向いている人： パッケージマネージャーに慣れている人。macOS ユーザーは Homebrew が特に便利です。

Windows ユーザーへの注意： WinGet は OS 標準ですが、Chocolatey と Scoop は別途インストールが必要です。同じソフトで 3 つを混ぜて使わないでください。「2 つ入って挙動がおかしい」状態になります。

言語のパッケージマネージャー（npm / pip / cargo など）

どんな形か：

1
2
3
4
5

npm install -g @anthropic-ai/claude-code   # Node.js のパッケージマネージャー
npm install -g opencode-ai
pip install xxx                             # Python のパッケージマネージャー
cargo install xxx                           # Rust のパッケージマネージャー
go install xxx                              # Go のパッケージマネージャー

何か： プログラミング言語ごとに、それぞれの「アプリストア」があります。npm は Node.js の、pip は Python の、cargo は Rust のものです。-g は「グローバルインストール」、つまり現在のプロジェクトだけでなくシステム全体に入れるという意味です。

長所： すでに Node.js / Python / Rust 環境があれば一番楽。プラットフォームをまたいで一貫している。

短所：

  • 対応するランタイムを先に入れる必要がある（npm なら Node.js）；
  • グローバルパッケージの更新は通常手動コマンド；
  • npm には同名の偽パッケージが存在するので、公式のパッケージ名を必ず確認すること。

向いている人： 普段からコードを書き、Node.js などの環境がすでにある人。

あなたが知っている npm はこの分類です。 それは「インストールツール」ではなく「言語エコシステムのパッケージマネージャー」です。

単体バイナリ / アーカイブ

どんな形か：

公式サイトや GitHub Releases からダウンロードします：

  • Windows：xxx-windows-x64.zip、.exe
  • macOS：xxx-macos-arm64.tar.gz、.dmg
  • Linux：.tar.gz、.deb、.rpm、.AppImage

展開して、中の実行ファイルをどこかのディレクトリに置き、そのディレクトリを自分で PATH に追加します。

何か： 公式がビルド済みの「完成品」を直接渡してくれるもので、中間業者は挟まりません。

長所： Node.js やパッケージマネージャーに一切依存しない。バージョンを厳密に管理できる。オフラインでもインストールできる。

短所： 更新は自分でダウンロードして差し替える。PATH は自分で設定する。アーキテクチャ（x64 / ARM64）を間違えると動かない。

向いている人： ランタイムを入れたくない人、クリーンで制御可能な状態を求める人、ネットワーク制限でスクリプトが使えない人。

コンテナ / Docker

どんな形か：

1

docker run -it --rm ghcr.io/anomalyco/opencode

何か： Docker は「隔離された箱」です。ツールは箱の中に入り、ホスト側のシステムには触れません。-it は対話的ターミナル、--rm は終了時にこの箱を自動削除するという意味です。

長所： クリーンで再現性があり、システムを汚さない。PC を替えても 1 コマンドで環境を復元できる。

短所： Docker を先に入れる必要がある。デスクトップ系ツールには向かないこともある。ファイルパスのマッピングに追加設定が要る。

向いている人： 開発者、環境を隔離したい人、サーバーにデプロイする人。一般ユーザーには通常不要です。

デスクトップアプリ / グラフィカルインストーラー

どんな形か： .exe、.msi、.dmg、.deb、.rpm、.AppImage をダブルクリック。

何か： コマンドラインを経由せず、GUI でインストールする版です。

長所： ターミナルに不慣れな人に最も優しい。画面があり、ボタンを押せる。

短所： CLI のすべての機能があるとは限らない。更新方法はプラットフォームごとに違う。CLI しか提供しないツールもある。

向いている人： ターミナルに一切触れたくない人。

ソースからビルドしてインストール

どんな形か：

1
2
3

git clone https://github.com/xxx/xxx
cd xxx
make && make install

あるいは cargo build --release、go build。

何か： ソースコードを取得し、自分の PC でコンパイルして実行ファイルにするものです。

長所： コードを改変できる。自分のプラットフォーム向けに最適化できる。未リリースのバージョンを入れられる。

短所： コンパイラツールチェーンが必要。時間がかかる。更新が面倒。エラーが出やすい。

向いている人： 開発者、ソースを改変したい人。一般ユーザーは選ばないでください。

アプリストア / プラグインマーケット

どんな形か：

  • VS Code 拡張機能マーケットでプラグインを検索；
  • JetBrains プラグインマーケットでプラグインを検索；
  • Microsoft Store / Mac App Store でアプリを検索；
  • ブラウザの拡張機能ストア。

何か： 何らかのホストソフトの中に入る「プラグイン版」であり、単体の CLI ではありません。

長所： インストールが最も簡単。ホストソフトとの統合が良い。

短所： 機能がホストソフトに制限される。ホストをアンインストールするとプラグインも消える。設定ファイルを再作成するプラグインもある。

向いている人： 特定のエディタ内だけで使いたく、単体の CLI を入れたくない人。

まとめの一覧表：どう選ぶか

方法 典型的なコマンド 事前インストール 自動更新 向いている人
公式ワンラインスクリプト curl … | bash / irm … | iex 不要 通常あり 最速で入れたい人
OS のパッケージマネージャー brew / winget / choco / scoop / apt 対応するパッケージマネージャー パッケージマネージャー次第 パッケージマネージャーに慣れた人
言語のパッケージマネージャー npm -g / pip / cargo 対応するランタイム 手動 Node/Python/Rust 環境がある人
単体バイナリ zip / tar.gz をダウンロード 不要 手動 ランタイムに依存したくない、バージョン管理したい
コンテナ / Docker docker run … Docker イメージを再取得 隔離環境・再現性を求める人
デスクトップアプリ .exe / .dmg をダブルクリック 不要 アプリ内更新 ターミナルを使いたくない人
ソースからビルド git clone + make コンパイラツールチェーン 手動 開発者、コードを変えたい人
アプリストア / プラグイン ストアでインストールをクリック ホストソフト ホストに従う エディタ内だけで使いたい人

ひと言での選び方：

公式ワンラインスクリプトが使えるならそれを使う。ネットワークやシステムの制限で詰まったら OS のパッケージマネージャーに退く。npm などの言語パッケージマネージャーは最後の手段。ランタイムに一切依存したくないなら単体バイナリ。ターミナルに触れたくないならデスクトップアプリ。

用語ミニ辞典

用語 意味
CLI Command Line Interface。ターミナルでコマンドを打って使うツールのこと。
ターミナル / Terminal コマンドを打つ黒い枠やウィンドウ。Windows では PowerShell、CMD、Windows Terminal。
PATH 「実行ファイルをどのディレクトリから探すか」をシステムに伝える環境変数。設定を誤ると command not found になる。
npm Node.js のパッケージマネージャー。インストール方法そのものではなく、「言語パッケージマネージャー」という分類で最も有名なもの。
irm PowerShell の Invoke-RestMethod。ネットから内容をダウンロードする。irm ... | iex = スクリプトをダウンロードして実行。
curl クロスプラットフォームのダウンロードツール。curl ... | bash = スクリプトをダウンロードして実行。
iex PowerShell の Invoke-Expression。テキストをコードとして実行する。
バイナリ / Binary コンパイル済みの実行ファイル。ダブルクリックかコマンドで動く。
ランタイム ある言語を動かすのに必要な環境。たとえば Node.js は JavaScript のランタイム。
グローバルインストール あるプロジェクトフォルダだけでなく、システム全体で使えるようにインストールすること。npm では -g。
Docker ソフトを箱の中に入れてホスト側に触れさせない「隔離された箱」ツール。
リポジトリ / Repository パッケージやソースコードを置く場所。GitHub が最も一般的なコードリポジトリ。
Releases GitHub の「公開バージョン」ページ。通常はビルド済みアーカイブが置かれている。

セキュリティ上の注意

  1. 公式ドメインからのみダウンロードする。 curl … | bash や irm … | iex を実行する前に、ドメインをよく確認する。

  2. npm のパッケージ名は公式のものだけを信じる。 npm には同名の偽パッケージがあり、間違って入れると認証情報が漏れる可能性がある。

  3. curl | bash の習慣： 可能なら先にスクリプトをダウンロードし、一度読んでから実行する：

    1
2
3

    curl -fsSL <url> -o install.sh
less install.sh
bash install.sh

  4. 署名 / チェックサムを検証する。 公式は通常 SHA256 や GPG 署名を提供している。重要なツールでは検証を推奨。

  5. 第三者の「設定切替 / 中継プロキシ」ツールは慎重に。 これらは設定ファイルを書き換え、第三者のアドレスやトークンを書き込むことが多く、軽ければエラー、重ければ認証情報の漏洩につながる。

  6. API Key を Git リポジトリにコミットしない。 漏洩が疑われたら、ただちに対応プラットフォームでローテーションする。

本記事は個人のまとめであり、公式ドキュメントではありません。正確なコマンドは各プロジェクトの公式ページを参照してください。
