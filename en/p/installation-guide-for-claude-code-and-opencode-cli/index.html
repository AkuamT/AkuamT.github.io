A command-line (CLI) installation manual for Windows / macOS / Linux, covering the two major AI coding assistants. Compiled in October 2026. Commands and versions follow the official docs; if anything here differs from the official pages, the official pages win. How to read: if you only want to install one tool, jump straight to that section; if you want to know “should I still use npm”, read the “Start Here” section.

Start Here: The Three Most Common Questions

Q1: Do I still need to install via npm?

Tool Verdict
Claude Code No. The official docs list the Native Install as Recommended, and npm has been moved to “Advanced installation options”. Moreover, only the native install updates automatically in the background — Homebrew / WinGet / npm all require manual upgrades. New users should avoid npm.
OpenCode Optional. The official project offers an install script, standalone native binaries, and npm. Users who already have Node.js will find npm the least effort; if you want no Node.js dependency at all, download the standalone binary.

Q2: Are there native installers / binaries?

Both exist.

  • Claude Code: one command with the native installer. No Node.js and no administrator privileges required — it configures PATH automatically and updates in the background.
  • OpenCode: the project ships standalone binaries for each platform (zip / tar.gz) plus an install script; however, on Windows the install script depends on a bash environment (WSL or Git Bash), which is why the official docs recommend WSL first for Windows.

Q3: How do I choose among the three approaches?

In one sentence: use the official native installer whenever you can; if network or system restrictions block you, fall back to a system package manager (WinGet / Homebrew / choco / scoop), and treat npm as the last resort.

What the Installer Does Behind the Scenes

Knowing the flow helps you tell “stuck” from “working”:

  1. Validate the system architecture (reject 32-bit Windows); pick the ARM64 or x64 binary automatically.
  2. Read the current version number from downloads.claude.ai.
  3. Download that version’s manifest.json and extract the SHA256 checksum for your platform.
  4. Download the binary to a local temporary directory.
  5. Verify the SHA256; on mismatch, delete the file and abort.
  6. Install into your user directory and write PATH.
  7. Delete temporary files and print a completion message.

⚠️ Two things that are easy to misjudge

  • There is no progress bar at any point, so it looks frozen while it is in fact downloading; it usually finishes within tens of seconds.
  • The completion marker is a green line reading Installation complete!.

Installation Locations

Platform Executable Data directory
Windows %USERPROFILE%\.local\bin\claude.exe %USERPROFILE%\.local\share\claude
macOS / Linux / WSL ~/.local/bin/claude ~/.local/share/claude

User configuration and session data live in ~/.claude/ (on Windows, %USERPROFILE%\.claude) and ~/.claude.json.

Verifying the Installation 

1
2

claude --version     # should print a version number
claude doctor        # environment self-check (first choice for troubleshooting)

Important: after installing, close and reopen your terminal. The PATH just written by the installer is not visible to windows that are already open.

If you get “command not found” (command not found / The term 'claude' is not recognized as the name of a cmdlet):

1
2
3

# Windows PowerShell
Test-Path "$env:USERPROFILE\.local\bin\claude.exe"                                  # ① is the binary installed?
[Environment]::GetEnvironmentVariable('Path','User') -split ';' | Select-String 'local\\bin'   # ② does PATH include it?

If ① is True while ② is empty, add it to the user-level PATH manually (no administrator needed, just append):

1
2

$p = [Environment]::GetEnvironmentVariable('Path','User')
[Environment]::SetEnvironmentVariable('Path', "$env:USERPROFILE\.local\bin;$p", 'User')

On macOS / Linux the same idea applies: add export PATH="$HOME/.local/bin:$PATH" to ~/.bashrc / ~/.zshrc.

First Run and Login 

1
2

cd your-project-directory
claude

The first launch starts a guided flow: choose a login method (a Claude subscription account, or an API key from the Anthropic Console) → finish authorization in the browser → configuration is written to ~/.claude/.

Do not want to use an official Anthropic account? You can point it at a third-party vendor’s Anthropic-compatible endpoint (DeepSeek / Kimi / Zhipu GLM / Qwen, etc.) and skip the login flow entirely — see “Skipping the Official Login: Connecting to Third-Party LLM APIs” below.

Update Strategy and Release Channels

  • Native install: updates automatically in the background, no intervention needed.
  • Release channels:
    • stable — the stable channel, usually about a week behind the newest version, and it skips releases with major regressions;
    • latest — the newest channel, available as soon as a version ships.
  • Update commands for the other methods: brew upgrade claude-code / winget upgrade Anthropic.ClaudeCode / npm update -g @anthropic-ai/claude-code.

Installing OpenCode

Website: https://opencode.ai | Repository: https://github.com/anomalyco/opencode

Note on the project’s history: it originally belonged to the sst organization and has since moved to anomalyco. The old link github.com/sst/opencode redirects automatically — it is not an impersonation site.

First, Understand V1 vs V2

OpenCode currently has two parallel product lines, and both use the opencode command, so they cannot coexist (you cannot install both):

V1 (stable) V2 (beta)
Install script curl -fsSL https://opencode.ai/install | bash curl -fsSL https://opencode.ai/v2/install | bash
npm package opencode-ai @opencode/cli
Homebrew brew install anomalyco/tap/opencode brew install anomalyco/tap/opencode-v2
Windows package managers choco / scoop supported Not supported
Docs https://opencode.ai/docs https://opencode.ai/v2/docs

Recommendation: V2 is still in beta and explicitly states that Windows package managers are unsupported. Choose V1 for stability; try V2 only if you want an early look, and remember it cannot coexist with V1.

Method Command

npm npm install -g @opencode/cli

When installing via npm / bun / pnpm, the package’s postinstall script automatically selects the native binary for the current platform. bun and pnpm block build scripts by default, which is why the official commands include --trust / --allow-build.

Three Things Windows Users Should Know

  1. WSL is officially recommended first: best performance and compatibility.
  2. The install script needs bash: curl ... | bash will not run in a plain Windows terminal; you need WSL or Git Bash.
  3. V2 does not support Windows package managers: the choco / scoop route is unavailable on V2; use npm or the standalone binary instead.

Install Directory Priority

The install script picks its destination in this order:

  1. $OPENCODE_INSTALL_DIR
  2. $XDG_BIN_DIR
  3. $HOME/bin
  4. $HOME/.opencode/bin (the default fallback)

Example:

1

OPENCODE_INSTALL_DIR=/usr/local/bin curl -fsSL https://opencode.ai/install | bash

Verifying and Configuring 

1
2

opencode --version    # print the version
opencode              # start the TUI inside a project directory

Once launched, use /connect inside the TUI to configure model providers (the official OpenCode Zen is recommended, but any compatible provider works).

Uninstalling

  • Script / standalone binary install: delete the opencode executable from the install directory chosen above and remove that directory from PATH.
  • npm install: npm uninstall -g opencode-ai (or @opencode/cli).
  • Homebrew: brew uninstall opencode (or opencode-v2).
  • Configuration directories: ~/.config/opencode/ and ~/.local/share/opencode/ can be deleted as needed.

Desktop Version (Beta)

If you would rather not use the terminal, the project also offers a desktop app: opencode-desktop-windows-x64.exe for Windows, .dmg for macOS, and .deb / .rpm / .AppImage for Linux; see the official docs for the download page.

Comparing the Two and How to Choose

Dimension Claude Code OpenCode
Made by Anthropic (official) Anomaly community, open source (MIT)
Model support Primarily the Claude family (also supports compatible API endpoints) Any provider (including local/self-hosted)
Installation difficulty Very low (one command, automatic updates built in) Medium (pick a method per platform/version)
Windows experience Good native support (installing Git for Windows is advised) WSL recommended
Open source Client is closed source Fully open source
Best for People who want “works out of the box + official support” People who want “swappable models, self-hosting, editable source”

How to choose

  • Just want to get going fast and you have an Anthropic account → Claude Code (native install).
  • Want third-party models, want to save money, want to tinker → OpenCode (V1 stable).
  • The two are similar in positioning, so you can install both: Claude Code lives in your user directory (~/.local/bin) while OpenCode goes through npm or its own directory, so they do not interfere.

Skipping the Official Login: Connecting to Third-Party LLM APIs

This section covers a mechanism Claude Code officially supports: pointing requests at your own LLM gateway, or at the Anthropic-compatible endpoints offered by third-party vendors (DeepSeek, Kimi, Zhipu GLM, Qwen, etc.). It is not a crack — the official docs have a dedicated page, Connect Claude Code to an LLM gateway, describing it. Once configured, Claude Code no longer requires an official Anthropic login.

Principle: Swap the URL and the Credential

Claude Code only recognizes one thing: the Anthropic Messages API protocol. Any service that speaks this protocol can replace the underlying model after you change a few environment variables.

Variable Purpose Consequence if missing
ANTHROPIC_BASE_URL The endpoint requests go to Requests still go to Anthropic; the third-party key fails authentication
ANTHROPIC_AUTH_TOKEN Credential, sent as Authorization: Bearer <token> A 401 authentication error
ANTHROPIC_API_KEY The other credential form, sent as x-api-key Same as above (interactive mode also asks for a one-time confirmation, see “Troubleshooting” below)
ANTHROPIC_MODEL The main conversation model “Model not found”
ANTHROPIC_DEFAULT_OPUS_MODEL
ANTHROPIC_DEFAULT_SONNET_MODEL
ANTHROPIC_DEFAULT_HAIKU_MODEL
ANTHROPIC_DEFAULT_FABLE_MODEL		 Model mapping for each tier Tasks in the corresponding tier fail
CLAUDE_CODE_SUBAGENT_MODEL The model used by sub-agents Sub-tasks fail or degrade noticeably

Which credential variable should you use? The official advice: when you are unsure which one the gateway expects, start with ANTHROPIC_AUTH_TOKEN; if you get a 401, switch to ANTHROPIC_API_KEY (and vice versa). Do not set both.

Why is the “tier mapping” mandatory? Claude Code requests different model tiers depending on the scenario — main conversation, background summaries, sub-agents, and so on. Third-party endpoints usually do not have names like haiku / sonnet / opus, so each tier must be explicitly mapped to a real model name; otherwise the corresponding scenario fails silently (the chat works, while background tasks error out).

Step 1: Get the endpoint and model names — see “Vendor Quick Reference” below, and always defer to each vendor’s official docs.

Step 2: Write the user-level configuration file

  • Windows: C:\Users\<username>\.claude\settings.json

    "ANTHROPIC_DEFAULT_OPUS_MODEL": "<model name>",

    "ANTHROPIC_DEFAULT_FABLE_MODEL": "<model name>",

Step 3: Skip the first-run login flow

Edit or create ~/.claude.json (Windows: C:\Users\<username>\.claude.json) and add this entry:

1
2
3

{
  "hasCompletedOnboarding": true
}

Without it, Claude Code tries to reach api.anthropic.com for a login check on startup, producing errors such as Unable to connect to Anthropic services. Failed to connect to api.anthropic.com: ERR_BAD_REQUEST.

A one-shot cross-platform write (using node to edit the JSON, so you cannot break the formatting by hand):

1

node --eval "const fs=require('fs'),p=require('path'),os=require('os');const f=p.join(os.homedir(),'.claude.json');const c=fs.existsSync(f)?JSON.parse(fs.readFileSync(f,'utf-8')):{};c.hasCompletedOnboarding=true;fs.writeFileSync(f,JSON.stringify(c,null,2),'utf-8')"

Step 4: Restart the terminal → launch claude → verify (see “Verifying the Configuration” below)

Where the Configuration Lives (Critical)

Location Scope Notes
env in ~/.claude/settings.json All projects (personal level) ✅ Recommended; the official docs and every vendor guide use it
Shell environment variables (export / $env:) The current terminal and its child processes Fine for temporary tests; but IDEs launched from the desktop/Start menu will not see them
env in a project’s .claude/settings.json That project only ⚠️ It takes effect after the first-run wizard and the trust prompt, so it cannot be used to skip login; it is also easy to commit into git by accident

Conflict rule: the env block in settings.json overrides environment variables of the same name from the shell. So when “I changed the environment variable but nothing happened”, go back and check whether settings.json still holds a stale value.

Vendor Quick Reference

⚠️ Endpoints and model names are maintained by each vendor and change frequently. The table below is only a starting point — always confirm against each vendor’s official docs before configuring.

Vendor ANTHROPIC_BASE_URL Example model names Official docs
DeepSeek https://api.deepseek.com/anthropic deepseek-flash, deepseek-v4-pro api-docs.deepseek.com
Kimi (Moonshot) https://api.moonshot.cn/anthropic kimi-k3[1m], kimi-k2.7-code platform.moonshot.cn
Zhipu GLM https://open.bigmodel.cn/api/anthropic glm-5.3[1m], glm-5.3-flash docs.bigmodel.cn
Qwen (Alibaba Cloud Bailian) Pay-as-you-go: https://dashscope.aliyuncs.com/apps/anthropic
Coding Plan: https://coding.dashscope.aliyuncs.com/apps/anthropic
Token Plan: https://token-plan.cn-beijing.maas.aliyuncs.com/apps/anthropic		 qwen3.7-plus, qwen3.6-flash, etc. help.aliyun.com

Three easy-to-miss details

  1. The [1m] suffix is valid — it means “1M context window”, not a typo; every vendor’s docs write it that way (e.g. kimi-k3[1m], glm-5.3[1m], qwen3.7-plus[1m]). You can express the same thing with the CLAUDE_CODE_MAX_CONTEXT_TOKENS environment variable.
  2. DeepSeek maps model names automatically: per its official docs, an unsupported model name is mapped to deepseek-flash on the backend; also claude-opus* → deepseek-v4-pro, and claude-haiku* / claude-sonnet* → deepseek-flash. This is why it can be wired into Claude Code by changing only a base_url.
  3. Do not append /v1 or /v1/messages to the endpoint yourself: Claude Code assembles the path on its own, and the extra segment usually yields a plain 404.

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.moonshot.cn/anthropic",
    "ANTHROPIC_AUTH_TOKEN": "YOUR_API_KEY",
    "ANTHROPIC_MODEL": "kimi-k3[1m]",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "kimi-k3[1m]",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "kimi-k3[1m]",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "kimi-k2.7-code",
    "ANTHROPIC_DEFAULT_FABLE_MODEL": "kimi-k3[1m]",
    "CLAUDE_CODE_SUBAGENT_MODEL": "kimi-k3[1m]",
    "CLAUDE_CODE_AUTO_COMPACT_WINDOW": "1000000",
    "CLAUDE_CODE_EFFORT_LEVEL": "max"
  }
}

What each parameter does:

  • ANTHROPIC_DEFAULT_HAIKU_MODEL usually points at a cheap, fast model (background summaries, small tasks), while the main tiers get strong models;
  • CLAUDE_CODE_AUTO_COMPACT_WINDOW: the window size that triggers automatic context compaction — set it too small and you lose context prematurely;
  • CLAUDE_CODE_EFFORT_LEVEL: reasoning effort; max gives the best quality, and is the slowest and most expensive.

Verifying the Configuration

Step Action Expected result
① Probe the endpoint directly curl <BASE_URL>/v1/messages --header "Authorization: Bearer <KEY>" --header "Content-Type: application/json" --data '{"model":"<model>","max_tokens":1,"messages":[{"role":"user","content":"hi"}]}' Valid JSON ({"id":"msg_...","content":[...]}), not an HTML error page
② Check inside a session Run /status after starting claude The Anthropic base URL line shows your endpoint; Auth token / API key shows the credential source. If it says Login method: <claude.ai account>, the credential never arrived
③ End to end Send any message (e.g. “hello”) A normal reply, no errors
④ Model tiers /model Your configured models are listed

After changing the configuration you must open a new terminal window before starting claude, or you will still be reading the old environment.

Troubleshooting

Symptom Cause Fix
401 invalid_api_key Credential type does not match the endpoint, or the key is invalid Pick either ANTHROPIC_AUTH_TOKEN or ANTHROPIC_API_KEY; confirm the key and endpoint belong to the same vendor and the same plan
model not found The model name is misspelled, or the model is not enabled on your plan Check the name against the vendor docs (watch the [1m] suffix, capitalization, stray spaces)
The main chat works but sub-agents / background tasks error out Tier variables are incomplete Add ANTHROPIC_DEFAULT_HAIKU_MODEL, ANTHROPIC_DEFAULT_FABLE_MODEL, CLAUDE_CODE_SUBAGENT_MODEL
Configuration changes have no effect A stale value lingers in settings.json, or an old export exists in the shell Clear both; settings.json’s env takes precedence over the shell
Still asked to log in / Unable to connect to Anthropic services The variables were not visible before the first-run wizard, or hasCompletedOnboarding is missing Use the user-level settings.json or a shell export; make sure the entry in ~/.claude.json is true
Every start asks Do you want to use this API key You are using ANTHROPIC_API_KEY (interactive mode needs a one-time confirmation) Choose Yes, or switch to ANTHROPIC_AUTH_TOKEN
Want to clear a saved official login You ran /login earlier Run /logout in a session, then restart
403 / an HTML error page An upstream WAF or reverse proxy blocked the request body Have the gateway exempt /v1/messages from request-body inspection rules

Important Reminders

  1. Never set ANTHROPIC_API_KEY and ANTHROPIC_AUTH_TOKEN at the same time — they conflict; Kimi’s docs explicitly tell you to delete ANTHROPIC_API_KEY.
  2. settings.json holds the key in plaintext: do not commit it; always add project-level configuration to .gitignore.
  3. .env files are not read: do not put credentials in a .env.
  4. Switching vendors means switching where your data goes: your code and conversations pass in full through that vendor or relay service — think it through beforehand, prefer vendor-operated endpoints, and be wary of “relay stations” of unknown origin.
  5. Going back to the official login: delete these variables from the env block in settings.json (or delete the file), run /logout, restart claude, and the official login flow returns.
  6. The trade-off of third-party “one-click switcher” tools: see “Managing Configuration with a GUI Tool” below — they rewrite settings.json directly, saving operational effort at the cost of far more expensive troubleshooting.

Managing Configuration with a GUI Tool (the CC Switch Trade-off)

Hand-writing settings.json is genuinely a barrier for people unfamiliar with JSON, so a number of “configuration manager / provider switcher” GUI tools have appeared. The most popular is CC Switch (github.com/farion1231/cc-switch, 140k+ stars, official site ccswitch.io). The analysis below applies to this whole class of tools.

What They Solve

  • Fill in Base URL / API Key in a GUI — no JSON, no fear of a stray comma;
  • Built-in templates for common vendors (DeepSeek, Kimi, Zhipu GLM, Qwen, etc.) plus self-hosted gateways;
  • One-click switching between multiple providers (official account ↔ third-party account ↔ cheap models);
  • Automatically write hasCompletedOnboarding for you, skipping the first-run login;
  • Extras such as backups, Skills management and usage statistics.

For users who switch frequently between several providers, this is genuinely convenient. It saves operational effort.

The Inherent Costs You Should Know

These tools do not “change one field for you” — they take over your configuration files. For CC Switch specifically, its own docs and issue tracker plainly record several “working as designed” behaviours:

Behaviour Consequence
Switching providers rewrites the live configuration file with a full snapshot (the maintainers state in issue #3946 that “this is intentional design”) Fields you wrote yourself in settings.json — hooks, statusLine, permissions, etc. — get overwritten; related issues include #2992 / #4274 / #2109 / #2871 / #3078
It writes its own hooks or environment variables, sometimes with helper scripts If the script body or its interpreter is missing on your machine, every launch errors — and the error is far away from anything labelled “configuration”, making it very hard to trace
A single program manages multiple CLIs at once (Claude Code / Codex / OpenCode / Gemini / Grok / Hermes, etc.) A misconfiguration in one place spills into the others. For example, when the path it writes for OpenCode differs from the path the tool actually reads, you get “switching looks successful but nothing took effect” (issue #5945)
It edits the real, live files, not a copy When something breaks, the crime scene is the very configuration you were working with

Note: this is usually not “poor software quality” but the nature of the product — takeover-style management inevitably creates “whose field wins” conflicts. It does offer backups (~/.cc-switch/backups/, plus backups/live-first-write/ recording the original file before the first rewrite), but backups save files, not the time you spend troubleshooting.

The Beginner-Friendliness Paradox

Hand-written configuration GUI tool
Getting started You need to read one JSON file A few clicks
Troubleshooting Every line is yours, so the search space is tiny You face a pile of generated files + overwritten originals + auto-injected hooks, unsure which layer is in effect
Scriptable diagnosis Yes (diff, /status, claude doctor, layer by layer) Usually no (pure GUI, no command-line entry point)

In other words: it saves operational effort and costs you troubleshooting effort. If you still have to search for why your configuration did not take effect, you will be even more lost when something the tool wrote for you breaks.

Decision Guide

Your situation Recommendation
One provider, long-term use Write the configuration once and you are done — nothing to touch for months. The minutes a GUI saves are not worth the overwrite risk
Frequent switching between 3+ providers This is where such tools earn their keep; worth using, but follow “If You Decide to Use One” below
You want minimalism Use the “template + one command” approach from the section above, or write a “switching = copy one small file” script — faster and more transparent than a GUI

If You Decide to Use One

  1. Let it manage only one tool: do not open the panels for CLIs you do not use (Codex / Gemini / OpenCode, etc.);
  2. Turn off local proxy / Routing: direct connections have one fewer layer that can fail;
  3. Turn off unnecessary auto-sync: Skills sync, session sync and plugin integrations all reach into other directories;
  4. Open the configuration file after every switch (~/.claude/settings.json): confirm the model names in env are right and that there is no leftover hooks section;
  5. Remember where the backups live: ~/.cc-switch/backups/live-first-write/ keeps “the original file before it was rewritten” — recover from there when things break;
  6. Run a self-check after switching (e.g. claude doctor);
  7. Be aware: doing all six of the above is, for a single-provider user, already more bother than writing one JSON file.

Security Notes

  • These tools touch your API keys and every configuration file, so download them only from official channels. CC Switch’s official site is ccswitch.io and its official repository is github.com/farion1231/cc-switch; several same-named forks exist on GitHub, so verify the author and URL before downloading.
  • Even cloud vendors that recommend it add a disclaimer. Alibaba Cloud’s Bailian docs, for instance, write: “This tool is third-party software; its scripts and code are not reviewed or maintained by Alibaba Cloud. Please assess the credibility of its source and the security of its code before installing or using it.”
  • Whatever tool you use, ~/.claude/settings.json is always what actually takes effect. Learn to read that file and you will always have a fallback.

Security and Compliance Notes

  1. Download only from official domains
    • Claude Code: claude.ai, code.claude.com, downloads.claude.ai
    • OpenCode: opencode.ai, github.com/anomalyco/opencode
  2. Only trust official npm package names: look-alike packages exist on npm (the OpenCode ecosystem even saw imitations such as opcpackage). Use @anthropic-ai/claude-code for Claude Code and opencode-ai (V1) / @opencode/cli (V2) for OpenCode.
  3. Verify signatures/checksums
    • Windows: Get-AuthenticodeSignature .\claude.exe, and the signer should be Anthropic, PBC.
    • macOS: codesign --verify --verbose ./claude.
    • The project also publishes a GPG-signed manifest.json that lets you verify the SHA256 of binaries on every platform.
  4. Safe habits for curl … | bash and irm … | iex: check the domain first, then run; when possible, download the script, read it, then run it (curl -fsSL <url> -o install.sh followed by less install.sh).
  5. The trade-off of third-party “config switcher / relay proxy” tools: see “Managing Configuration with a GUI Tool” above. The core point — they rewrite ~/.claude/settings.json, ~/.config/opencode/opencode.json and similar files directly, and those files are always what actually takes effect, so you must be able to read, edit and verify them.
  6. API key management: never commit keys in plaintext to a Git repository; if a key is suspected of leaking, rotate it on the relevant platform immediately.
