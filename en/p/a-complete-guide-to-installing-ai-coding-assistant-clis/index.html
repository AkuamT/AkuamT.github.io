First, Understand What “Installing” Actually Does

No matter which method you pick, installing a command-line tool really only does three things:

  1. Put an executable file into some directory on your computer (such as claude.exe or opencode).
  2. Tell the system where that directory is (that is, configure PATH), so that typing claude anywhere can find it.
  3. Possibly write some configuration files along the way (such as ~/.claude/ or ~/.config/opencode/).

The difference between installation methods is simply “who does these three things for you”:

  • Official script: a program written by the vendor does it for you.
  • Package manager: a piece of software called a “package manager” does it for you.
  • Manual download: you do it yourself.
  • Docker: put it inside an isolated box instead of your host system.

Once you understand this, all the methods below become easy.

Eight Installation Methods, One by One

Official One-Line Script

What it looks like:

1
2
3
4
5
6
7
8

# macOS / Linux / WSL
curl -fsSL https://xxx.com/install.sh | bash

# Windows PowerShell
irm https://xxx.com/install.ps1 | iex

# Windows CMD
curl -fsSL https://xxx.com/install.cmd -o install.cmd && install.cmd && del install.cmd

Decoding it word by word:

  • curl: a download tool; -fsSL means “quiet, fail on error, follow redirects, show errors”.
  • | bash: feed whatever was downloaded straight into bash to execute.
  • irm: the download command in PowerShell (short for Invoke-RestMethod).
  • | iex: feed whatever was downloaded straight into iex to execute (short for Invoke-Expression).

So irm ... | iex and curl ... | bash are the same idea written for two platforms: download a script → run it immediately.

What it does for you: identifies your system automatically (Windows or Mac, 64-bit or ARM), downloads the right build, verifies the file, places it in a directory, and configures PATH. You type one line.

Pros: the least effort; usually includes automatic updates; no need to pre-install a runtime such as Node.js.

Cons: “download and execute” — you cannot see the script before it runs; you must confirm the domain is the official one.

Who it suits: people who want the fastest setup and are fine trusting the official script. This is currently the recommended path for most AI CLI tools.

System Package Managers

What it looks like:

Tool Platform Example
Homebrew macOS / Linux brew install xxx
WinGet Windows winget install xxx
Chocolatey Windows choco install xxx
Scoop Windows scoop install xxx
apt Debian / Ubuntu sudo apt install xxx
dnf Fedora sudo dnf install xxx
pacman Arch Linux sudo pacman -S xxx
apk Alpine sudo apk add xxx

What it is: a “software repository” maintained by the OS or the community. You tell it what to install, and it downloads, unpacks, configures, and registers it — and later also handles upgrades and removal.

Pros: clean upgrade and uninstall paths; well integrated with the system; no need to remember install paths.

Cons: versions in the repository often lag behind; many newly released AI CLI tools never make it into these repositories at all.

Who it suits: people already used to package managers; Homebrew is especially convenient for macOS users.

Note for Windows users: WinGet ships with the system, while Chocolatey and Scoop must be installed separately. Do not mix the three for the same piece of software, or you may end up with “two copies installed and weird behaviour”.

Language Package Managers (npm / pip / cargo, etc.)

What it looks like:

1
2
3
4
5

npm install -g @anthropic-ai/claude-code   # Node.js package manager
npm install -g opencode-ai
pip install xxx                             # Python package manager
cargo install xxx                           # Rust package manager
go install xxx                              # Go package manager

What it is: every programming language has its own “app store”. npm belongs to Node.js, pip to Python, cargo to Rust. -g means “global install”, that is, installed system-wide rather than only into the current project.

Pros: if you already have a Node.js / Python / Rust environment, this is the smoothest route; consistent across platforms.

Cons:

  • You must install the matching runtime first (npm needs Node.js, for instance);
  • global packages usually require a manual command to upgrade;
  • look-alike packages with the same name exist on npm, so you must use the official package name.

Who it suits: people who already write code and already have Node.js or similar on their machine.

The npm you know belongs to this category. It is not “an installer”, but “a package manager for a language ecosystem”.

Standalone Binaries / Archives

What it looks like:

Download from the official site or GitHub Releases:

  • Windows: xxx-windows-x64.zip, .exe
  • macOS: xxx-macos-arm64.tar.gz, .dmg
  • Linux: .tar.gz, .deb, .rpm, .AppImage

Unpack it, move the executable inside into a directory, and add that directory to PATH yourself.

What it is: the vendor hands you a pre-built “finished product” with no middleman involved.

Pros: no dependency on Node.js or any package manager; precise version control; installs offline too.

Cons: upgrading means downloading and replacing it yourself; PATH must be configured manually; picking the wrong architecture (x64 / ARM64) means it will not run.

Who it suits: people who want no runtime at all, who want a clean and controllable setup, or who cannot run scripts due to network restrictions.

Containers / Docker

What it looks like:

1

docker run -it --rm ghcr.io/anomalyco/opencode

What it is: Docker is an “isolated box”. The tool lives inside the box and never touches your host system. -it means an interactive terminal, --rm means the box is deleted automatically on exit.

Pros: clean, reproducible, no pollution of your system; moving to a new computer restores the environment with one command.

Cons: Docker must be installed first; not necessarily suitable for desktop tools; file path mapping requires extra configuration.

Who it suits: developers, people who want isolation, people deploying on servers. Ordinary users generally do not need it.

Desktop Apps / Graphical Installers

What it looks like: double-click .exe, .msi, .dmg, .deb, .rpm, .AppImage.

What it is: a version installed through a graphical interface instead of the command line.

Pros: friendliest for people unfamiliar with the terminal; there is a UI with buttons to click.

Cons: may not expose all the abilities of the CLI; updating differs across platforms; some tools only ship a CLI with no desktop version.

Who it suits: people who would rather not touch the terminal at all.

Building From Source

What it looks like:

1
2
3

git clone https://github.com/xxx/xxx
cd xxx
make && make install

Or cargo build --release, go build.

What it is: you take the source code and compile it into an executable on your own machine.

Pros: you can modify the code, optimize for your platform, or build versions that have not been released yet.

Cons: requires a compiler toolchain, takes a long time, upgrades are painful, and errors are common.

Who it suits: developers, people who want to change the source. Ordinary users should avoid this.

App Stores / Plugin Marketplaces

What it looks like:

  • search for plugins in the VS Code extension marketplace;
  • search for plugins in the JetBrains plugin marketplace;
  • search for apps in the Microsoft Store / Mac App Store;
  • browser extension stores.

What it is: a “plugin version” that lives inside some host application, not a standalone CLI.

Pros: the simplest installation, well integrated with the host application.

Cons: capabilities are limited by the host application; uninstalling the host removes the plugin too; some plugins recreate configuration files.

Who it suits: people who only want to use it inside a particular editor and do not want a separate CLI.

One Summary Table: How to Choose

Method Typical command Requires pre-install Auto update Who it suits
Official one-line script curl … | bash / irm … | iex None Usually yes People who want the fastest setup
System package manager brew / winget / choco / scoop / apt The matching package manager With the package manager People already used to package managers
Language package manager npm -g / pip / cargo The matching runtime Manual People who already have Node/Python/Rust
Standalone binary download zip / tar.gz None Manual No runtime dependency, version control
Container / Docker docker run … Docker Pull the image again Isolation and reproducibility
Desktop app double-click .exe / .dmg None In-app update People who avoid the terminal
Build from source git clone + make Compiler toolchain Manual Developers who change code
App store / plugin click install in the store Host application With the host People who only use an editor

One-line recommendation:

If the official one-line script works, use it. If network or system restrictions block you, fall back to a system package manager. Treat language package managers such as npm as the last resort. If you want no runtime dependency at all, use a standalone binary. If you do not want to touch the terminal, use a desktop app.

Glossary

Term Meaning
CLI Command Line Interface. The tool you use by typing commands in a terminal.
Terminal The dark box or window where you type commands. On Windows: PowerShell, CMD, Windows Terminal.
PATH An environment variable that tells the system “which directories to search for executables”. If it is misconfigured you get command not found.
npm The package manager for Node.js — not an installation method itself, but the most famous member of the “language package manager” category.
irm Invoke-RestMethod in PowerShell, used to download content from the internet. irm ... | iex = download a script and run it.
curl A cross-platform download tool. curl ... | bash = download a script and run it.
iex Invoke-Expression in PowerShell; it executes a piece of text as code.
Binary An already-compiled executable that runs when you double-click it or type its command.
Runtime The environment a language needs in order to run; Node.js is the runtime for JavaScript, for example.
Global install Installed so the whole system can use it, rather than only one project folder. In npm this is -g.
Docker An “isolated box” tool that keeps software inside the box, away from the host system.
Repository A place that stores packages or source code. GitHub is the most common code repository.
Releases The “published versions” page on GitHub, usually holding pre-built archives.

Security Notes

  1. Download only from official domains. Before running curl … | bash or irm … | iex, check the domain carefully.

  2. Only trust official npm package names. Look-alike packages exist on npm; installing the wrong one can leak your credentials.

  3. A good curl | bash habit: when possible, download the script first, read it, then run it:

    1
2
3

    curl -fsSL <url> -o install.sh
less install.sh
bash install.sh

  4. Verify signatures / checksums. Vendors usually publish SHA256 or GPG signatures; verify them for important tools.

  5. Be careful with third-party “config switcher / relay proxy” tools. They often rewrite your configuration files and inject third-party endpoints and tokens — at best you get errors, at worst your credentials leak.

  6. Never commit API keys into a Git repository. If a key is suspected of leaking, rotate it on the relevant platform immediately.

This document is a personal write-up, not official documentation. For exact commands, refer to each project’s official pages.
